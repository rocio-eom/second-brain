# ADR: 형상관리 층 네이밍 — 궤적의 이름과 릴리스 태그

## 상태

Accepted (2026-09-10). [[dec-2026-09-10-code-layer-naming-taxonomy-and-enforcement]]의 **확장**이며 개정이 아니다 — 그쪽이 코드베이스 안에 놓인 것의 이름을 가져왔다면 이것은 그 변경이 이동한 궤적의 이름을 가져온다. 회고 예정: 2026-10-08.

플랫폼 저장소 쪽 대응 ADR: `platform-data-model` ADR 0013.

## 배경 (Context)

[[dec-2026-09-10-code-layer-naming-taxonomy-and-enforcement]]이 이 문제를 이름 붙여 두고도 확장하지 않았다.

> **에이전트가 쓴 것을 다음 세션의 에이전트가 다시 찾아야 한다**(navigation paradox). 읽기 최적화와 쓰기 규범이 같은 규칙이 아니면 세션이 바뀔 때마다 이름이 표류한다.

그리고 규칙 자체는 **이미 [[dec-2026-07-31-git-repo-topology-naming-convention]]의 D4 에 있었다** — *"커밋/브랜치: Conventional Commits + commitlint, GitHub Flow"*. 그 노트의 회고가 내린 판정이 이 결정의 출발점이다.

> **D1·D2 의 결정 내용은 유효하다. 실패한 것은 강제다.** … 네 어긋남 중 셋이 같은 원인을 갖는다 — 규칙은 적혔고 검사는 없었다.

회고는 **코드 층만 실측했다.** 그 결과가 ADR 0012 로 해소됐고, 형상관리 층은 실측되지도 해소되지도 않은 채 남았다. commitlint 는 끝내 설치되지 않았다.

실측(2026-09-10)한 오염은 이미 시작돼 있었다.

| 대상 | 실측 | 무엇이 깨지는가 |
|---|---|---|
| 태그 ↔ 커밋 | design-system 태그 4건 중 **2건이 릴리스 커밋이 아닌 곳에** (`v1.0.0` → `feat(react): TextField 에 date 추가 (#12)`) | 태그에서 릴리스 경계를 읽을 수 없다. 사고조사가 여기서 이미 끊긴다 |
| 태그 ↔ 버전 | changesets 는 독립 버전인데 태그는 `v1.2.0` 하나 | 그 시점에 각 패키지가 몇이었는지 태그가 답하지 못한다 |
| 커밋 문법 | 최근 30건 중 2건 위반 | 전수 검사는 첫날 빨개진다 |
| 브랜치 | 살아 있는 6건 전부 이슈 번호 없음 | 회수 시점에 "아직 살아 있어야 하는가"를 물을 곳이 없다 |
| 커밋 스코프 | 플랫폼 4개는 "최상위 디렉토리", design-system 은 "패키지 이름" | 같은 규칙의 두 인스턴스인데 두 규칙으로 적혀 있었다 |
| 강제 | commitlint · PR 템플릿 · 훅이 **워크스페이스 전체에 0건** | D4 가 예측한 실패가 그대로 남아 있었다 |

## 결정 (Decision)

### D1. 필드열은 `[{actor}/]{kind}/{issue}-{slug}` 다

좌에서 우로 일반에서 구체로 간다. `platform-infrastructure` ADR 0007 이 클라우드 리소스 이름에 세운 원리 그대로이며, 거기서 `prod-*` 가 권한 경계가 되듯 **여기서는 `agent/*` 한 줄이 회수 경계가 된다.** actor 를 첫 필드에 둔 것이 그 이유이고 유일한 이유다.

`human/` 은 두지 않는다 — 접두가 모든 이름에서 같은 값이면 정보가 아니라 비용이다. 값이 하나뿐인데 자리를 잡아 두는 것은 나중에 끼워 넣는 것이 전면 개명이기 때문이다.

불변식 둘이 파싱을 지킨다: `actors` ∩ `commits.types` = ∅, 그리고 slug 는 숫자로 시작할 수 없다. 정본 자신에 대해 검사한다 — **불변식이 깨지면 그 뒤의 모든 판정이 조용히 틀린다.**

### D2. 하나의 키는 `{issue}-{slug}` 다

워크트리 디렉토리가 브랜치의 **접미**이고, 세션 로그와 `Session:` 트레일러가 같은 값을 쓴다. 병렬 에이전트 세션에서 어느 세션이 무엇을 만들었는지 경로 하나로 특정된다. **필드 순서를 뒤집으면 이 키가 사라진다.**

워크트리는 `{workspaceRoot}/.worktrees/{repo}/{issue}-{slug}` 다. 저장소 안에 두면 코드 층 감사가 워크트리 안의 `packages/` 를 또 읽어 중복 이름으로 오탐한다. `{repo}` 세그먼트는 실측 때문이다 — 같은 이름의 브랜치가 두 저장소에 동시에 존재한 적이 있다.

### D3. 티켓은 GitHub Issue 번호이고, 크로스리포 조인은 slug 가 한다

채번기를 새로 만들지 않는다. 대신 **repo-scoped 라는 사실을 감추지 않는다.**

앵커 저장소의 번호를 모든 저장소가 쓰는 안을 기각한 이유는 구체적이다 — GitHub 이 남의 `#12` 를 자기 저장소 이슈로 자동 링크해 **엉뚱한 이슈에 조용히 연결한다.** 그래서 `{issue}` 는 언제나 그 저장소의 자기 번호이고, 조인은 `{slug}` 가 하며, 앵커는 완전 수식 `Anchor: {owner}/{repo}#{n}` 트레일러가 담는다.

**이 결정의 알려진 약점**: slug 는 자유 문자열이라 기계가 오타를 잡지 못하고, 검증하려면 형제 저장소를 읽어야 하는데 CI 에 PAT 이 없다. **ADR 0012 가 부딪힌 것과 같은 벽**이므로 새 예외를 만들지 않고 기존 리뷰 체크리스트에 한 줄을 더했다.

### D4. 로스터는 한 곳에만 둔다

브랜치의 `kind` 는 커밋의 `type` 과 **같은 로스터를 참조한다.** 브랜치 정규식은 구조만 보고 값은 로스터가 판정한다. 두 곳에 적으면 브랜치는 `feat` 인데 커밋은 `fix` 인 상태가 정상이 되고, 브랜치명으로 변경 성격을 읽는 일이 무의미해진다.

같은 이유로 **PR 제목과 커밋 제목을 같은 함수가 판정한다.** squash merge 가 PR 제목을 커밋 제목으로 만들기 때문이고, 두 문법이 다르면 스쿼시된 순간 린터를 통과할 수 없는 커밋이 `main` 에 굳는다. 그 위반은 되돌릴 수 없다.

스코프 갈라짐도 같은 방식으로 해소했다 — 두 규칙은 대립이 아니라 **같은 규칙의 두 인스턴스**였다. 스코프는 변경이 닿은 최상위 워크스페이스 단위이고, 그 단위가 무엇인지는 저장소 이름이 아니라 **마커**(발행 가능한 워크스페이스의 존재)가 판정한다. 릴리스 태그의 형태도 같은 마커를 쓴다.

### D5. 에이전트 표식은 중립 접두 + 가변 트레일러다

브랜치 접두는 **중립 `agent/`** 이고 벤더명은 `Agent: {vendor}/{model}` 트레일러가 담는다. ADR 0007 의 *"이름은 불변 식별자이고 태그는 가변 메타데이터다"* 그대로다 — 브랜치명은 회수 필터의 인덱스라 값이 바뀌면 필터가 깨지고, **벤더를 브랜치에 넣으면 벤더를 바꿀 때 브랜치 문법이 바뀐다.**

AI 공시는 PR 라벨 `authored-by:ai` / `authored-by:human` 중 **정확히 하나**다. 기본값이 없으면 "라벨 없음"이 *AI 가 아님* 과 *붙이는 것을 잊음* 둘 다를 뜻해 공시가 성립하지 않는다.

도구가 기본으로 붙이는 `Co-Authored-By` · `Claude-Session` 은 로스터에서 뺐다 — 여러 저장소의 작업 규약이 이미 그것을 금지하고 있고, 같은 사실을 `Agent:` 가 기계가 읽을 수 있는 형태로 담는다.

### D6. 태그는 패키지별 SemVer 이고, 아티팩트 좌표는 그 파생이다

`packageName → tag → artifactCoord` 가 하나의 유도 사슬이다. 모노레포는 `@scope/pkg@X.Y.Z`, 단일 패키지 저장소는 `vX.Y.Z` 이며 판정은 D4 의 마커가 한다. 모노레포에서 `v*` 태그는 금지한다 — 두 형태가 섞이면 어느 것이 최신인지 정렬로 정할 수 없다.

**태그는 `chore(release):` 커밋에만 붙는다.** 실측 위반 2건이 정확히 이 규칙의 부재였다.

사고조사의 역추적 사슬에서 **git 이 채우지 못하는 고리는 `digest → 태그` 하나뿐이고** attestation 이 그것을 채운다. 나머지(태그→커밋, 커밋→PR·이슈·주체)는 git 과 트레일러가 이미 갖고 있다. **그래서 릴리스 매니페스트 파일을 만들지 않는다** — 만들면 git 이 이미 아는 사실의 두 번째 사본이 생긴다.

### D7. 강제는 조립 독점 → 훅 → CI 순이고, PDP 는 쓰지 않는다

승격 순서는 **유도 → 절차 → 강제**다. 이름을 만드는 지점을 조립기 하나로 묶어 위반이 애초에 생기지 않게 하고(`gen-vcs-name.mjs`), 훅이 빠른 피드백을 주고, CI 가 게이트다. 훅은 clone 시 자동 설치되지 않으므로 **훅이 없어도 CI 가 같은 판정을 내야 한다.**

PDP 정책은 만들지 않는다. 근거 셋 중 결정적인 것은 **정책 엔진에 정규식 부정 연산자가 없다**는 사실이다 — "규약을 안 지키면 위반"을 쓰려면 부정 lookahead 정규식을 정책 파일에 적어야 하고, 그 순간 정본이 둘이 된다. governance 자신이 금지한 상태다.

훅과 CI 가 둘 다 검사하는 것은 "두 곳"이 아니다. 금지된 두 곳은 **두 정본**이고, 셋이 같은 엔진 함수를 부르므로 정본은 하나다.

## 고려한 대안 (Considered options)

| 대안 | 기각 사유 |
|---|---|
| 현행 유지 | 실측된 오염이 이미 넷이다. 그리고 D4 의 회고가 "규칙은 적혔고 검사는 없었다"를 이미 판정했다 |
| `conventions/vcs.yaml` 신설 | kebab-case 가 세 번, npm 스코프가 두 번 선언된다. `packageName → tag` 유도가 두 파일을 가로지른다 |
| PDP 정책으로 강제 | 정규식 부정 연산자 부재 + 평가 경로 미도달 + governance 선례. 평가되지 않는 정책은 비워 두는 것보다 나쁘다 |
| 벤더 접두 `claude/` | 벤더를 바꿀 때 브랜치 문법이 바뀐다. 회수 필터가 깨진다 |
| 단일 `v*` 태그 유지 + 락스텝 | 토큰만 고쳐도 react 가 같이 올라가고 소비자가 의미 없는 major 를 받는다. changesets 가 이미 독립을 선언했다 |
| CalVer | 소비자의 range 해석 입력이 `package.json.version` 인데 CalVer 는 호환성 정보를 담지 않는다 |
| 릴리스 매니페스트 파일 | git 이 이미 아는 사실의 두 번째 사본. CI 가 `main` 에 쓰면 브랜치 보호와 싸운다 |
| 이력 전수 검사 | 고치는 방법이 history rewrite 뿐이고, **그러면 사람들이 규칙을 끈다** |

## 결과 (Consequences)

**좋은 점**

- 워크트리 경로 하나에서 브랜치·세션 로그·커밋 트레일러가 역산된다 (병렬 세션 격리)
- `agent/*` 한 줄로 방치 브랜치가 전부 잡힌다 (일괄 회수)
- 발행본 digest 에서 커밋·PR·이슈·주체까지 한 사슬로 간다 (사고조사)
- 에이전트가 릴리스 태그를 **짓지 않고 유도한다** — 채번은 changesets, 조립은 도구, 에이전트는 실행만
- 규약을 고치면 사람이 읽는 사전이 자동 재생성되고, CI 가 재생성 동일성을 강제한다

**나쁜 점 / 비용**

- `Refs: #{issue}` 가 항상 필요하므로 **이슈 없이 커밋할 수 없다.** 이 워크스페이스에 이슈 체계가 없었고 도입 비용이 여기 실린다
- 저장소마다 `.githooks/` 와 PR 템플릿을 한 번 켜야 한다
- `release.yml` 이 5곳 바뀐다. 트리거를 안 고치면 **발행이 조용히 누락된다**

**제약**

- 크로스리포 slug 일치는 기계가 못 본다 (D3 의 알려진 약점, ADR 0012 와 같은 벽)
- 소급은 유예가 아니라 `enforcedSince` 경계다. **고칠 방법이 없는 것에 만료를 주는 것은 거짓말이다**
- `platform-governance/exceptions/` 는 이 규약에 쓸 수 없다 — 면제할 정책이 없고 `subject` 가 브랜치를 지목하지 못한다. 적어 두지 않으면 사람들이 없는 절차를 찾다가 규칙을 우회한다

## 트레이드오프

**형태의 정본을 한 파일에 몰았다.** `conventions/naming.yaml` 이 950줄이 됐다. 대신 kebab-case 도 npm 스코프도 한 번만 선언되고, 층 사이 유도가 한 파일 안에서 닫힌다. 파일이 커지는 비용보다 정본이 갈라지는 비용이 크다는 판단이며, **세 절이 케이스 규칙과 약어사전을 공유하지 않게 되는 날**이 분리 트리거다.

**강제를 기본으로 켜지 않았다.** 재사용 워크플로의 `vcs` 입력은 기본 `false` 다. 켜는 순간 그 저장소의 이력이 판정 대상이 되므로 도입 시점을 저장소가 고른다. 대신 **끈 것을 통과로 세지 않기 위해** 워크플로가 사유를 남긴다 — 조용한 통과가 이 플랫폼의 알려진 사인이다.

## 후속 (Follow-ups)

- [ ] 파일럿 저장소를 정하고 19스텝 파이프라인을 **실행으로** 한 바퀴 돌린다. 핵심 검증 둘: 패키지별 태그가 실제로 그 패키지만 발행시키는가, `gh attestation verify` 가 digest 에서 커밋까지 도달하는가
- [ ] `design-system` 은 `allowedActions: []` 라 **에이전트가 고칠 수 없다.** 파일럿을 그 저장소로 하려면 사람이 하거나 잠금을 여는 별도 결정이 필요하다
- [ ] 이슈 체계 도입 비용을 실측한다 — `Refs:` 가 필수인데 현재 이슈가 0건이다
- [ ] 컨테이너 이미지 좌표는 유예했다. GHCR/ECR 첫 push 가 트리거다
- [ ] `feature-improvement.workflow.yaml` 의 `platform/change` 리터럴은 **고치지 않았다** — 그 워크플로에 실행 경로가 없어 `{issue}` 를 채울 수 없고, 리터럴만 고치면 규약을 지킨 것처럼 보일 뿐이다
